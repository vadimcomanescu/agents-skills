Long-Running Skill Pipeline — Design Review v3

Seven phases, none of which survive the deletion test if cut. Backbone: jarrodwatts long-running-agent. Loops: trycycle. Style: Mat Pocock principle-first. v3 changes: Design re-added; Spec uses Pocock's LANGUAGE vocabulary (module / interface / seam / depth — what survived from DDD); reviewer prompt structure surfaced verbatim.

Sessions are durable event logs, not the model's context window. Anthropic, Scaling Managed Agents, Apr 8 2026 — anthropic.com/engineering/managed-agents
Generation must be separated from evaluation — models grade themselves too generously. Addy Osmani, Long-running Agents, Apr 28 2026 — addyosmani.com/blog/long-running-agents

Style. Pocock principle-first: each phase leads with one italicized sentence stating the rule, then unpacks. Deletion test (Pocock, LANGUAGE.md): every phase ends with the answer to "if I delete this phase, what complexity vanishes?" If the answer is "nothing meaningful", it gets cut. Five phases were cut from v1 — see the cuts section below for what and why.

Research

phase 0

The orchestrator coordinates research; it never researches itself. Parallel subagents go and look — externally first (best practices, prior art, pitfalls), then at the codebase, then a cross-reference pass to find gaps. The output is a contract for downstream phases.

Coordinator (host model) Research-analyst × N (Claude, web) Explore × N (Haiku, codebase) User approval gate
Trigger
User states a goal in natural language.
Workflow
  1. Classify intent. TRIVIAL / REFACTOR / GREENFIELD / MID_SIZED / BUG_FIX. Drives question count and downstream rigor (smart-ralph). TRIVIAL skips this phase entirely.
  2. Decompose into research topics. One topic per subagent. No topic touches both web and codebase — separate concerns.
  3. Dispatch in one message. Parallel subagents: research-analyst for each external topic, Explore for each codebase concern.
  4. Cross-reference pass. Compare external best practices against current codebase. Flag gaps and deviations. This is the architectural-shift mechanism.
  5. Synthesize partial files into one research.md. Approval gate: user reviews recommendations + open questions before phase 1 opens.
Output
.agent/research.md — sections: Executive Summary, External Research (Best Practices / Prior Art / Pitfalls), Codebase Analysis, Quality Commands (lint/test/build), Verification Tooling, Feasibility, Recommendations, Open Questions, Sources. Quality Commands and Verification Tooling tables are consumed by Plan and Review.
Boundary
Coordinator never writes research content. Never makes architectural decisions here — those go in Spec. Research only surfaces options + evidence.
"The research command is a coordinator, not a researcher. It MUST delegate ALL research work to subagents... The coordinator never performs web searches, codebase analysis, or writes research.md content itself." smart-ralph references/parallel-research.md
External-first cross-reference is what shifts architectural decisions. Without it, the build perpetuates whatever pattern the codebase already has — even when the industry has moved past it.
Deletion test: Cut Research and the Spec phase invents architectural decisions from training-data priors instead of from current best practice. The Beck "make change easy first" rule (gstack) cannot fire because the agent doesn't know what "easy" looks like in the current ecosystem. Verdict: keep.

Discover

phase 1

The goal must be small enough to bound the build. Research surfaced options; Discover narrows to one. The output is the only document that says what "done" means.

Claude (conversation) User approval gate
Trigger
After Research is approved.
Workflow
  1. Read research.md. Don't re-ask anything research already answered.
  2. Ask only what's ambiguous. Question count gated by intent class from phase 0 (TRIVIAL: 0-1, GREENFIELD: 5-10).
  3. Write goal.md. Problem / Outcome / Acceptance Criteria (measurable) / Non-Goals.
  4. Approval gate. User edits or approves. After this, the orchestrator goes autonomous.
Output
.agent/goal.md. Pocock cut: no Tech Stack here, that's a spec-level decision; no "Vision" or "Mission" sections.
Boundary
No design here. No tasks. Discover is the smallest possible artifact that bounds the build.
"ask the model to make incremental progress towards its goal while also leaving the environment in a clean state... the agent tended to try to do too much at once — essentially to attempt to one-shot the app." Anthropic, Effective harnesses for long-running agents, Nov 26 2025
A bounded goal is the only thing that prevents one-shotting. "Build me a SaaS" fails; "build the auth flow with email + Google OAuth, Postgres-backed sessions, no MFA" succeeds.
Deletion test: Cut Discover and acceptance criteria live in someone's head. Review (phase 5) has nothing to verify against; subagent reports become "I implemented something" with no falsifier. Verdict: keep.

Spec

phase 2

Specs and implementation are separate ralphs. Spec writes user stories (extensive), decisions (paragraphs, not formal ADR ceremony), and the module list using Pocock's vocabulary. Critic reviews independently before the human gate opens.

Claude (writer) Codex (critic) User approval gate (HTML)
Trigger
After goal.md is approved.
Workflow
  1. Writer drafts spec.md. Sections in order: Concepts (the words this system uses — see vocab below), User Stories (extensive — Pocock keeps this long), Decisions (each: one paragraph stating decision + why + alternative rejected), Modules (name + interface + what it hides + deletion-test answer).
  2. Critic reviews independently. Different model. Reads research.md + goal.md + draft spec. Returns: agreed / disagreed-on-X / missing-Y.
  3. Resolve. Writer addresses critic feedback. If critic and writer can't agree, surface to user.
  4. HTML gate. Human sees: decision diff (writer's choices side-by-side with critic's flags), module table with interface-vs-depth assessment, user story list, concepts table. Approve or edit.
Output
.agent/spec.md — single file. No adrs/ directory. Pocock: "An ADR can be a single paragraph. Most ADRs won't need Status / Considered Options / Consequences sections."
Boundary
No tasks here. No file paths in the spec (Pocock: "they may end up being outdated very quickly") except where a schema or state machine IS the decision.
Vocab (what survived from DDD)
Pocock retired his ubiquitous-language skill and "aggregate" as a load-bearing artifact. He kept the substance under precise vocabulary in his improve-codebase-architecture/LANGUAGE.md:
  • Module — anything with an interface + implementation. Scale-agnostic. Avoid: unit, component, service.
  • Interface — everything a caller must know to use the module correctly: signature + invariants + ordering + error modes + perf. Avoid: API, signature (too narrow).
  • Depth — leverage at the interface. Behavior exercised per unit of interface learned. Deep = lots of behavior behind small interface.
  • Seam (Feathers) — a place to alter behavior without editing in place. Avoid: boundary (overloaded with DDD's bounded context).
  • Adapter — concrete thing that satisfies an interface at a seam. Role, not substance.
  • Context — a slice of the system with its own language. (Pocock kept the concept; renamed from "bounded context".)
  • Deletion test — imagine deleting the module. If complexity vanishes, it wasn't hiding anything. If complexity reappears across N callers, the module was earning its keep.
  • One adapter = hypothetical seam. Two adapters = real seam. Don't introduce a seam unless something actually varies across it.

Spec phase uses these words. The "Modules" section of spec.md applies the deletion test to every proposed module — that's the bar.

"I had ralph write the specs from that, and I had another ralph build the implementation from the specs... if the specs are bad, the results will be meh." HumanLayer, A Brief History of Ralph, Aug 2025
Two-phase spec/build is the cheapest way to get planning rigor without orchestration overhead. The critic role is Osmani's "separate generation from evaluation" applied at spec time — different model catches different blind spots.
Deletion test: Cut Spec and Plan (phase 4) writes tasks against an ambient understanding of what to build. Deep-module extraction doesn't happen, so Plan emits shallow modules with chatty interfaces — merge-conflict hell when phase 5 parallelizes. Verdict: keep.

Design

phase 3

Motion and interaction can't be described, only felt. When the build has UI, the user must see it before approval — not read about it. Design produces a clickable HTML prototype the user navigates, not a written spec they read.

Claude (designer) User approval gate (HTML — IS the artifact) conditional: skip when no UI scope (gstack rule)
Trigger
After spec.md is approved AND spec contains UI scope. Skip for backend-only / library / pure-refactor work (gstack plan-design-review skip rule).
Workflow
  1. Designer reads spec.md. Extracts user stories that imply screens. One screen per primary user job — aggressively trimmed.
  2. Drafts design tokens. Colors, typography, spacing — small palette. tokens.css.
  3. Drafts screens.html — single self-contained file, clickable navigation between screens, real-looking states (loading / empty / error / success). No real backend; mocked data inline.
  4. HTML gate IS the artifact. Human opens screens.html, clicks through, says approve / cut screens / merge screens. The user's edits to the HTML (or notes about what to change) are the spec input for Plan.
Output
.agent/design/screens.html + .agent/design/tokens.css. Both consumed by Plan and Build subagents — workers reference the design when building UI tasks.
Boundary
No production code in screens.html — it's a mock. No state management, no real APIs. The design is a contract for what to build, not a head-start on the build itself.
"Motion and interaction can't be described, only felt." Thariq Shihipar, html-effectiveness
Markdown specs of UI hide failures that show up the moment a human clicks. Catching "this flow is wrong" at design time costs minutes; catching it after Build phase 5 costs hours of subagent work and an 8-round Review loop.
Deletion test: Cut Design and UI scope decisions live in the Spec's user-story prose. Build phase produces UI subagents will read prose and guess; Review phase has no visual reference to compare against. The "is this the right flow" question gets discovered at the Review HTML gate (phase 6) when the cost to fix is 50× higher. Verdict: keep, with skip-when-no-UI rule.

Plan

phase 4

Make the change easy, then make the easy change. Tasks are atomic (≤3 files, ≤50 LOC, single test). Refactors and behavior changes never share a task. The plan-editor loop runs up to 5 rounds — bugs found here cost 10× less than bugs found in code.

Claude (planner) Codex (critic, fresh per round) Plan-editor loop ×5 User approval gate (HTML)
Trigger
After spec.md is approved (and design/ exists if UI scope).
Workflow
  1. Planner decomposes. Spec + design (if present) → atomic tasks. Each task: ≤3 files, ≤50 LOC, single named acceptance test, single dependency direction.
  2. Tag each task as refactor or behavior (Beck/gstack rule — never both in one task).
  3. Build the DAG. depends_on per task. Parallelizable tasks marked. Max 5 in flight at any time (jarrodwatts).
  4. Plan-editor loop. Fresh planner per round critiques the current plan; returns READY or REVISED. Up to 5 rounds. If still REVISED after round 5: stop, dispatch analyzer subagent for why convergence failed, surface to user (trycycle).
  5. HTML gate. Human sees: task DAG visualization, refactor-vs-behavior balance, depth/width metrics, parallel-wave estimate. Approve or trim.
Output
.agent/tasks.json — array of task objects with id, kind (refactor|behavior), files, acceptance, depends_on, estimated_minutes.
Boundary
No code in the plan. No "TODO: implement X" tasks — every task has a falsifiable acceptance signal. No bulk test plans (Pocock: "tests written in bulk test imagined behavior").
"Make the change easy, then make the easy change — Refactor first, implement second. Never structural + behavioral changes simultaneously (Beck)." gstack plan-eng-review/SKILL.md (Cognitive Patterns #13)
Mixing refactor and behavior in one task makes the diff unreviewable and the failure mode unattributable. The 5-round plan-editor cap comes from trycycle — diminishing returns past round 3, hard stop at 5.
Deletion test: Cut Plan and Build (phase 5) gets a spec instead of tasks — workers immediately conflict because nothing serializes the order. The 5-parallel cap (jarrodwatts) cannot be enforced. Plan-editor loop has nothing to operate on. Verdict: keep.

Build

phase 5

One task per worker invocation. Commit, push, promise NEXT, stop. Workers run in isolated worktrees. Models alternate Claude/Codex per task — the reviewer in phase 5 will be the opposite model.

Coordinator (host) Worker × ≤5 (Claude or Codex)
Trigger
After tasks.json is approved. Continuous: as soon as a task's depends_on is satisfied, it's eligible.
Workflow
  1. Coordinator picks the next eligible task. Re-reads tasks.json + progress.md before every dispatch (jarrodwatts: state files are working memory).
  2. Spawns a worker subagent in an isolated git worktree. Model assignment: alternate Claude/Codex; record which.
  3. Worker writes the test first (TDD), then the code. Runs make check && make test. Captures evidence (screenshot/golden/trace) into .agent/evidence/<task-id>/.
  4. Worker commits, pushes, outputs <promise>NEXT</promise>, and stops. No multi-task workers.
  5. Coordinator updates progress.md with task result + which model + commit hash + evidence path.
Output
Git commits + .agent/evidence/<task-id>/ + .agent/progress.md updates.
Boundary
Worker never decides scope. Never modifies files outside its declared files. Never weakens or deletes tests to reach green (trycycle). Never starts the next task itself.
"HARD STOP: Implement exactly ONE feature per invocation. Commit, push, output promise, stop." ralph-to-ralph build-prompt.md:190
Single-task-per-invocation is what makes the parallel coordinator pattern work. If a worker chains tasks, it accumulates state, which defeats the "specialized subagents with clean context" rule (Anthropic, effective context engineering).
Deletion test: Cut Build and you have nothing. (Trivially survives.) The interesting question is: would removing the HARD STOP constraint matter? Yes — a worker that chains tasks reads more files, accumulates context, and produces less reviewable diffs. The discipline is what makes the pipeline work. Verdict: keep, with HARD STOP discipline.

Review

phase 6

If you haven't seen the code do the right thing, the code doesn't work. A judge subagent — opposite model from the worker — verifies against runtime evidence. Trycycle post-impl loop runs up to 8 rounds. Test ratchet: never accept weakened tests as green.

Judge (opposite model) Post-impl review loop ×8 User approval gate (HTML, per milestone)
Trigger
After every task commit. Per-task review is automatic. Per-milestone HTML gate is where the human approves.
Workflow
  1. Judge reads the task spec, the diff, and the evidence folder. Different model from the worker — Osmani: models grade themselves too generously.
  2. Verify against runtime evidence. Run the test, open the screenshot, replay the API call. Husain: telemetry tells the agent whether it worked.
  3. Test-ratchet check. Diff old vs new test files; flag any deletions or weakened assertions. (Osmani's anti-cheat mechanism.)
  4. If issues: resume the same worker (trycycle persistent session) with structured feedback. Up to 8 rounds. Stop and dispatch analyzer if not converged.
  5. Per-milestone HTML gate — human sees evidence wall: screenshots, video thumbs, test results, judge verdicts. Approve or send fixes. (Willison: one significant change at a time — humans approve milestones, not every task.)
Output
.agent/evidence/<task-id>/ contains: before.png, after.png, flow.webm (≤30s) for UI; request.http, response.json, golden.json for API; report.md with judge verdict + quoted assertions for pure logic.
Boundary
Judge never modifies code (only the worker does). Judge never weakens its own criteria. The HTML gate is the only place humans approve completed work — no per-task human review.
"separate generation from evaluation matters because models grade their own work too generously... a test ratchet sits in the prompt to stop the very common failure of an agent deleting failing tests." Addy Osmani, Long-running Agents, Apr 28 2026
8 rounds (vs Plan's 5) because code fixes are slower than text edits — same wall-time budget, more iterations available. Opposite-model judge is ralph-to-ralph's Claude-builds-Codex-QAs principle applied per-task.
Deletion test: Cut Review and the build rots silently. Workers report success, no one verifies, the orchestrator updates progress.md based on worker self-reports, you wake up to a green build that doesn't actually work. The Willison principle — "a computer can never be held accountable; that's your job as the human" — is unenforceable without a runtime-grounded judge. Verdict: keep, this is the load-bearing phase.
Reviewer prompt structure
The judge runs this prompt verbatim each round. Source: trycycle/subagents/prompt-post-impl-review.md.
[Identity] You are an independent code reviewer performing a detailed review. Review the diff between {WORKTREE_PATH} and merge base against: - {IMPLEMENTATION_PLAN_PATH} (finalized plan from phase 4) - {TEST_PLAN_PATH} (finalized test plan) [Inputs to read first] - The finalized implementation plan - The finalized test plan - Relevant files and repository context - Read-only git inspection commands as needed - Do NOT modify files [Review for] - Mismatches: implementation vs plan - Mismatches: tests vs test plan - Correctness and logic issues - Missing edge cases - Security and performance problems - Error-handling gaps - Missing or incorrect tests - Mismatches: implementation vs intended behavior - Doing things the right way, without taking shortcuts - SKIPPED TESTS — run the test suite yourself. ANY skipped test is a critical blocking issue, regardless of why (env gating, missing tools, missing env vars — none of these are acceptable reasons). Tests that were weakened, deleted, or had assertions loosened to pass are also critical blocking issues. [Output — exactly one block, no prose around it] <review_observations_json> { "status": "no_issues" | "issues_found", "summary": "short summary", "observations": [ { "id": "R1", "severity": "critical" | "major" | "minor" | "nit", "category": "implementation_plan_mismatch" | "test_plan_mismatch" | "correctness" | "edge_case" | "security" | "performance" | "error_handling" | "missing_test" | "behavior" | "other", "expected": "what should have happened", "observed": "what actually happened", "where": { "file": "rel/path", "line": 123, "symbol": "name" }, "evidence": { "commands": ["exact read-only commands you ran"], "stdout_excerpt": "...", "stderr_excerpt": "...", "traceback_excerpt": "...", "artifacts": ["paths"], "notes": "..." } } ] } </review_observations_json> [Rules] - Preserve observed evidence. Prefer command output, artifacts, and precise mismatches over advice. - Include where.file and where.line when possible. - Do NOT invent command output, tracebacks, or artifacts you did not actually inspect. - Use status:"no_issues" with empty observations only when no issues were found.
Loop wrapper
  1. Round 1: Coordinator dispatches a fresh judge subagent (different model from the worker that built this task). Judge returns the JSON block above.
  2. Extract. Coordinator runs review_observations.py extract to get authoritative blocking_issue_count, has_blocking_issues, review_status. If extraction fails, stop and surface — never guess.
  3. If blocking_issue_count == 0: task complete. Coordinator updates progress.md, closes the worker, moves on.
  4. If blocking issues remain: resume the same worker subagent (persistent session) with the JSON observations as fix input. Worker fixes, commits. Then a fresh judge runs round 2.
  5. Stop conditions: blocking_issue_count == 0, OR 8 rounds completed.
  6. If still red after round 8: dispatch an analyzer subagent to review past sessions and hypothesize why convergence failed. Surface to user with the analysis. Do NOT loop further.
Why this shape
  • Fresh judge per round — same judge across rounds anchors on its first read; fresh judge re-derives. Pattern from trycycle.
  • Persistent worker across rounds — worker has the context of what it just tried; restarting loses that. Pattern from trycycle.
  • Different model judge vs worker — Osmani: "models grade their own work too generously". Claude-built tasks reviewed by Codex; Codex-built reviewed by Claude.
  • Structured JSON output — orchestrator parses programmatically. No "the reviewer said it's mostly fine" subjective drift.
  • Explicit skipped-test rule — single most common cheat in autonomous loops. Made critical-blocking by name.
  • 8 rounds, then analyzer — past round 5 you're usually thrashing; the analyzer surface gives the human enough information to intervene without dumping 8 round transcripts.

Trycycle loops (where they sit)

Plan-editor loop · phase 4 (Plan), max 5 rounds

Fresh planner subagent per round. Returns Plan verdict: READY|REVISED. Stops with user surface if not converged. Cheap iterations on text edits — front-loaded here because plan bugs are 10× cheaper than code bugs.

Post-implementation review loop · phase 6 (Review), max 8 rounds

Fresh judge per round (opposite model from worker). Returns structured blocking_issue_count. Persistent worker session for fixes. 8 rounds because code iterations are slower than text — same wall-time, more rounds.
